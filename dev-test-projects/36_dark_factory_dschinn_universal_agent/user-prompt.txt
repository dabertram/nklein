I want to build the master challenge: a governed, deterministic control plane for an autonomous software-and-business factory. This is a SIMULATION of that factory with real architecture — not a chatbot, not a dashboard demo, and not a claim that the business itself works.

Read all of specification.md before planning. This is the maximal dev-test challenge intended to stress autonomous decomposition, local GPU/unified-memory inference, blue-green brain updates, persistent memory, market research, software-product creation, marketing, financial governance, plugin self-extension, self-improvement, long-running multi-project orchestration, and polished operator UX.

The product should demonstrate STRICTER governance, evidence handling, local-model adaptation and software-factory integration than comparable systems (that is measurable; "beating" fast-moving projects is not). Concretely it is: local-first but cloud-capable, chat-controlled but autonomously operating, two-brain update-safe, memory-rich, product-factory oriented, financially governed, evidence-led, and able to improve itself through plugins and tested code changes.

Plan the ~51-card VERTICAL SPINE first and implement it before planning the rest. Do NOT produce 400-650 cards up front: a fixed card count rewards fragmentation over plan quality, creates a huge stale plan before any architectural assumption is tested, multiplies false dependencies, and incentivises 600 plausible-looking cards whether or not they are needed. The sequence is: (1) plan the 51-card spine, (2) implement and validate it against the INDEPENDENT oracle, (3) REPLAN from what implementation actually taught you, (4) expand one capability family at a time, (5) stop when every requirement has coverage — not when a counter reaches 650. (If you want to test graph rendering/scheduling at 650 nodes, that is a SEPARATE generated graph-scale test; do not let a quantity benchmark distort the architecture benchmark.) Track knowledge debt explicitly: current model landscape, model licensing, benchmark relevance, local hardware economics, cloud cost, financial/legal constraints, marketing compliance, payment safety, platform ToS, security boundaries, plugin supply-chain risk, memory ethics, and owner-approval policy.

Build the real foundation first: typed domain model, two-brain lifecycle, model intelligence crawler fixtures, hardware profiler fixtures, persistent memory, project portfolio scheduler, opportunity research pipeline, product-factory workflow, financial governance ledger, tool gateway, plugin permission system, self-improvement lab, audit trail, and polished cockpit/chat view models.

Do not start with decorative chat UI. Do not create an unrestricted money-moving bot. Do not depend on live payments, live ads, live cloud deployments, real purchases, live LLM calls, or uncontrolled web access for acceptance tests. Use deterministic adapters for all external systems.

The system must be ambitious but governed: it can propose buying hardware, renting cloud GPUs, connecting frontier models, launching ads, publishing products, sending owner payouts, or reinvesting revenue only through explicit policies, budget limits, approvals, audit logs, and rollback/mitigation plans.

Very strong presentation is mandatory. The owner needs a cockpit: brain room, market radar, product portfolio, factory pipeline, money room, self-improvement lab, approval queue, emergency stop, and chat control room.

Prefer a smaller number of release-quality vertical slices over broad placeholder content. Every model update, spend proposal, product thesis, task priority, memory update, plugin install, public action, and self-improvement proposal must be explainable from source facts and covered by deterministic tests.

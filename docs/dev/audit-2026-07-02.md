## COMPREHENSIVE (10 dimensions)

### Executive summary

The dominant theme, confirmed by grep, is a large "built-but-unwired core" debt: the marquee mechanisms across nearly every dimension exist as pure, tested modules with ZERO live consumers outside their own cluster. Verified dark cores include cache-stable-prefix ordering, sysprompt-level/JIT-fragment tiering, reasoning-output-budget, best-of-N decomposition self-consistency, the online retrieval loop, selectSwarmRoleModel (end-to-end auto-assignment), penalizeFitnessByRuntimeVerdict, per-role ledger blend, work-package merge/conflict-resolution, and the entire durable-* family. !Klein's differentiating intelligence is written but not running.

Second theme — the operator experience (§5.AU) has no UI at all: the main ChatSidebar is bound to `getRuntimeTrpcClient(null)` (no workspaceId), can't render reasoning/tools/markdown/DAG, has no stop/cancel, no "talking to X" chip, and never receives server-pushed chat messages. The product thesis ("chat is the interface, board is its planning brain") is entirely unrepresented.

Third theme — reliability/correctness in the stateflow: errored cards run the delivery/merge gate on non-existent work with hard-coded testsPassed/reviewApproved=true; error/park paths never capture a result branch and never dispose the sandbox (pool exhaustion); failed/parked blockers permanently orphan their dependents; and "exit"/empty-patch runs auto-complete with no evidence gate. The ledger records errored and delivered runs identically, poisoning the very model-selection evidence stream.

Fourth theme — durability is the single largest missed dimension: all session state is in-memory Maps, no rehydrate path exists, and startup destructively reaps EVERY sandbox container — so any restart/crash silently destroys all in-flight swarm work and leaves a lying board. There is also no swarm-level integration test harness, making the "wire the dark cores" project dangerously unguarded.

Fifth theme — the small-vs-large adaptation the audit was scoped around is almost entirely absent: skill resolution, prompt generation, context budgeting, retrieval depth, and decomposition strategy are all model-blind. The dials to differentiate a 4B reasoning model from a 120B MoE (effective-window derate, sysprompt tiering, /no_think, fragment trimming, best-of-N, per-tier retrieval) are built but not fed a capability input.

Sixth theme — cross-cutting gaps no per-dimension audit owned: no out-of-band notifications for an away operator, no token/compute budgeting, no autonomous merge (hard-abort on first conflict), no board↔session↔container reconciler, and reasoning-diversity (architect≠reviewer lineage) — the user's newest steer — has no code and the catalog's `family` slug can't even express lineage.

Recommended sequencing: build the swarm integration harness and durability/reconciliation FIRST (they are the safety net and the biggest reliability holes), then the stateflow evidence/delivery gate, then wire the highest-leverage dark cores (cache-prefix, effective-window derate, best-of-N, per-role ledger, diversity), then the §5.AU chat UI, treating small-vs-large adaptation as the input that lights up cores as they're wired.

### Prioritized items

**1. [high/XL] (Completeness / cross-cutting) Durability + startup reconciliation: stop destroying in-flight swarm work on restart**
- WHY: Highest reliability value and genuinely hard: all session state is in-memory Maps with no rehydrate path (grep confirms zero restore/reattach in nklein-agent), and startup destructively docker-rm's EVERY labeled container, leaving cards 'running' on the board with no session. A crash or intentional restart silently destroys all in-flight work — fatal for a long-running unattended swarm. Cross-cuts stateflow, routing, and context.
- CHANGE: Persist each running card's launch config + last terminal state via the existing agent-attempt-ledger-store jsonl substrate; wire durable-run-registry/run-state-machine. On startup, BEFORE reaping, reconcile persisted 'running' sessions: re-attach to a still-alive labeled container (docker ps by slot) or mark interrupted+reviewReason. Make reapOrphanResources skip containers being resumed.

**2. [high/L] (Completeness / testing) Swarm-level integration/e2e harness with a scripted fake model**
- WHY: This is the prerequisite safety net for everything below: dozens of 0-caller cores must be wired, and the stateflow audit already found the cascade/reconcile/merge interplay is subtly buggy. 642 unit tests cover pure cores but nothing exercises decompose→route→run→cascade→review→merge end-to-end. Hard because it requires a deterministic fake LocalLlmClient and driving runtime-server through full multi-card boards.
- CHANGE: Build a deterministic harness with a scripted fake model (canned decompositions + card outcomes incl. errors/empty-patches/conflicts/truncation) that drives runtime-server through a full board and asserts lane transitions, dependency release, merge ordering, and no-orphan/no-strand invariants. Run in CI. Include small-model failure shapes.

**3. [high/M] (Card & session stateflows) Split the terminal contract so errored/no-delivery cards can't run the merge gate on non-existent work**
- WHY: P0 correctness bug, verified severe: isReviewableNKleinSummary returns true for reviewReason==='error', finalizeHeadlessAutoReviewTask then hits the delivery gate with HARD-CODED reviewApproved:true/testsPassed:true and invokes mergeTaskWorktreesInDependencyOrder on a card with no result branch. An errored/half-done card is actively pushed toward completion. Compounds the ledger-poisoning bug (errored runs scored as delivered).
- CHANGE: Introduce a distinct non-delivered terminal (session stays failed, or add reviewReason 'no_delivery'); make isReviewableNKleinSummary false for error/no-evidence cards; gate finalizeHeadlessAutoReviewTask on positive delivery evidence (non-empty result-branch commit); stop hard-coding testsPassed/reviewApproved. Make the evidence gate the single terminal authority so exit/empty-patch with no branch never auto-completes.

**4. [high/M] (Card & session stateflows) Capture result branch + dispose sandbox on error/park; add sandbox reaper**
- WHY: High value and hits the strict-isolation prime directive: emitTaskFailure calls emitSummary directly, bypassing finalizeSandboxReview, so error→awaiting_review never captures the patch (partial work lost, e.g. run7 interrupted mid write_files) and never disposes the container. With a small isolation pool, repeated errors/parks exhaust capacity and stall ALL future starts. Small models hit this hardest.
- CHANGE: On error path: (a) best-effort patch capture into the result branch before emitting terminal so partial work is inspectable/resumable; (b) always disposeWorkspace + forgetSandboxTask on both failed(park) and error→awaiting_review branches; add a periodic reaper for sandboxes whose session left running.

**5. [high/M] (Stateflows / cross-cutting) Board↔session↔container reconciler + failed-blocker dependency release**
- WHY: Two linked high-value gaps: (a) a failed/parked blocker never leaves the review column so getLinkedBacklogTaskIdsReadyAfterTaskTrashed early-returns and dependents orphan permanently — one parked mid-graph card strands an entire downstream subtree silently; (b) any out-of-band death (crash, reap, OOM) leaves the board asserting a running card that is dead. operator-board-health reads the same volatile state so a dead card looks healthy.
- CHANGE: Add a periodic reconciler cross-checking board lane ↔ session enum ↔ live container (docker ps by label), driving divergences to interrupted+reviewReason and releasing/holding dependents. Implement the chosen failed-blocker policy (mark-blocked-with-reason vs auto-retry-N vs wait). Make the reconciler the single authority operator-board-health reads. Retry deferred-overlap set on ANY transition out of an active state, not only completion.

**6. [high/L] (Context optimization) Wire cache-stable-prefix ordering + effective-window derate into the live prompt path**
- WHY: Biggest raw-speed lever for large models AND biggest quality lever for small ones, both verified dark. On a local single-GPU box prefill is THE bottleneck (~5s vs ~200s at 40k, up to 93% TTFT loss) yet the live prompt is raw string concat with no fragment model. Separately, budgeting uses the ADVERTISED window while learnedQualityEffectiveBudget (only printed to a dev console) implements the derate — so a 4B advertising 32k is budgeted as if all 32k are usable, the exact collapse case. Efficiency rules are also appended AFTER the date, defeating the append-at-end cache design.
- CHANGE: Introduce a fragment-based assembler in nklein-task-session-service: tag static/persistent/session/volatile fragments, run orderFragmentsForStablePrefix + assembleCacheAwarePrompt, record reuseRatio. Move buildKanbanEfficiencyRules' volatile budget numbers to the suffix beside the date; add a detectVolatilePrefixContent assertion. Thread learnedQualityEffectiveBudget into resolveKnownContextWindowForTask so all budgeting/compaction uses the derated window; surface advertised-vs-effective.

**7. [high/L] (Context / Prompts) Wire sysprompt-level tiering + JIT fragment budgeting into worker/decompose/review assembly**
- WHY: The single biggest small-vs-large lever, fully built and unit-tested but importable only by tests and each other. Today a 4B/32k model gets the same ~14k full-fat prompt (~44% of window gone before the task) as a 120B; contextScope affects exactly one line of text. This is the concrete mechanism to serve L0/minimal to tiny models and L4/max to large ones.
- CHANGE: Wire buildRequestEconomyPlan/classifyTaskComplexity/selectSysPromptLevel into the send seam; make buildKanbanEfficiencyRules accept a SysPromptLevel and drop optional packs (read_large_file workflow, Requirements Extraction) below 'balanced'; resolve the adaptive pack HOST-side instead of asking the model to self-select. Make contextScope actually select a level.

The operator cannot see streams, drill stream→DAG→card→thread, address a message, or see a card mailbox — even though the cores/schema/mailbox are shipped. **9. [high/L] (Auto model-selection) Reasoning-diversity constraint (architect≠reviewer lineage) — the user's newest steer, no code exists**

Surface the decision in model-selection-reason.

**Current state:** Decomposition validity is enforced in three shipped layers. (1) Per-task sizing/reference validation: `validateNKleinPlanTaskGraph` (plan-task-validation.ts:117) runs the zod schema, `validateTaskSizingContract` (complexity ≤75, ≤3 likely files, acceptanceCommand present), `validateTaskGraphReferences` (dup ids, dangling `dependsOn`), plus per-task routing feasibility. **Small-vs-large adaptation:** The validity strategy should invert by tier. LARGEST models (120B MoE, reliable tool-calls): default N=1 one-shot is fine; they can carry the whole-graph mental model, so lean on schema + strong coherence violations as hard gates and even ask them to run an architect self-check tool (§5.AV direction 4) to prove validity. Grammar-constrained decode (§5.AV direction 2) must be reasoning-aware and is likely viable only on the non-reasoning strong tier given the json_schema dead-end already found on the resident reasoning models.

## SWARM-BEHAVIOR (3 dimensions)

### Executive summary

The audit spans three dimensions — compute-efficiency, review-modelling, and multi-agent deliberation — and they converge on one structural truth: !Klein has built beautiful, tested PURE cores (retry-policy/adaptive-attempt-loop, second-opinion-review with acceptanceSummary plumbing, auto-clarify's bounded debate loop, the capability catalog) that are NOT WIRED into the live swarm session path. The single most damaging pattern is the auto-merge delivery gate at src/server/runtime-server.ts:567-569, which hardcodes reviewApproved=true, testsPassed=true, regressionDelta=null — so acceptance never hard-gates merge, a skipped/errored/no-verdict review counts as approval (fails OPEN), and errored/budget-parked cards deliver as if cleanly completed. This is a safety hole in a local-only autonomous system and should be closed first; it is also small effort because the plumbing exists and just needs to be threaded through. Verified against the tree: no planNextAttempt/applyThinkingDisable references in src/nklein-agent (retry ladder and /no_think are chat-only), no acceptanceSummary populated in second-opinion-review-runner.ts, and no lineage field in model-capability-catalog.ts (only per-entry family slugs in prose) — so family-diverse decision roles are literally unenforceable and the live architect=reviewer=gpt-oss-120b monoculture slipped through unchecked.

The three dimensions share dependencies, which drives the ordering. Fail-closed delivery (review) and wiring the retry ladder + /no_think (efficiency) are the two biggest independent wins and can proceed in parallel. Deliberation is the highest-ceiling but most speculative dimension, and it BLOCKS on a cheap prerequisite — the catalog needs a coarse lineage enum before any diversity term, arbitration, or panel can be enforced; that atom (effort S) should ship early even though the deliberation engine itself is later. A recurring theme across all three: waste and monoculture are currently INVISIBLE (no per-delivered-card efficiency metric, no diversityWaived flag, no deliberation record), so building the measurement/observability substrate is what makes every other fix tunable and every regression detectable. Recommended posture: fail-closed on missing evidence, flag-gate the retry-ladder wiring so 'park on truncation' stays default until measured, auto-apply /no_think only gated on difficulty (and fix the token-count-only difficulty estimator so that gate isn't misfed), group all qwen3_x variants as ONE lineage, and make deliberation on-by-default but trigger-gated to high-stakes+low-confidence with a per-run budget so it fires rarely.

**Current state:** The swarm has a genuinely good SCHEDULING/ROUTING layer for compute efficiency, but its two biggest token-burn mitigations are NOT wired into the live swarm path, and its start orchestration wastes host CPU on redundant subprocesses.

What exists and works:
- Free-first fan-out: `selectRoleModel` (src/core/role-model-selection.ts) and `selectSwarmRouteForTask` prefer idle models so parallel cards spread instead of queueing on one model. `isModelFree` combines own-session tracking with optional queue-aware `lms ps` busy detection (src/trpc/runtime-api/start-task-session.ts:411-449).
- Smallest-sufficient weighting ("efficient" default) reserves strong machines for hard cards (role-model-selection.ts:90-99, model-pool-routing.ts:85-96).
- Over-serialization was already partly fixed: the file-overlap guard now only serializes on SHARED SPECIFIC source paths and ignores coarse manifest/lockfile/config basenames (src/core/task-file-overlap.ts:36-81), so a defensively-listed package.json no longer blocks a wide DAG.
- Deferred-overlap cards are remembered and retried on the next completion instead of orphaning (runtime-server.ts:316-334, 608-614).
- The retry ladder IS failure-mode-targeted and deterministic-truncation-aware IN THEORY: `aborted` tries `raise_token_budget` FIRST (root-cause fix) before a plain re-run, so it should avoid temp-0 re-truncation loops (retry-policy.ts:56-61); `planNextAttempt` skips already-tried rungs (no circles) and always parks (retry-policy.ts:100-113).
- Capability gate refuses a catalog-`reject` model up front rather than burning a whole task (start-task-session.ts:253-267).
- Loaded-model residency uses a TTL cache (lmstudio-loaded-models.ts:60-85).
- Ledger records tokensPerSec + contextTokens per attempt (agent-attempt-ledger.ts:125,216,464-482).

The gap: the theory in retry-policy.ts and model-thinking-control.ts is only wired into the CHAT adapter (chat-local-llm-adapter.ts:179-180) and unit tests — NOT the nklein swarm session runtime. grep for planNextAttempt/adaptive-attempt-loop/applyThinkingDisable across src/nklein-agent returns nothing (only a comment reference). So the swarm gets neither /no_think suppression nor the raise_token_budget re-truncation fix on real cards.

**Small-vs-large adaptation:** The two unwired mitigations matter MOST at opposite ends of the spectrum. /no_think suppression (finding 2) is a pure win on small switchable reasoning models (qwen3-4b/8b), where ruminating 500-965 tokens on a trivial card is a large fraction of the whole turn and the top truncation cause — for a 120B fast non-reasoning model it's a no-op. Conversely raise_token_budget (finding 1) matters MOST for the always-reason families (qwen3.5/3.6, r1 distills, phi-4-reasoning) that IGNORE /no_think — for them a bigger budget is the ONLY recovery, and these are often the large capable models where a wasted full-context re-truncation is the most expensive single event. Difficulty mis-estimation (finding 5) wastes the strong/large models (over-provisioning easy cards occupies the exact machines the efficient-weighting tries to reserve) while starving weak small models into failure→route-up double-work. The hopelessness short-circuit (finding 6) protects the fleet's most expensive compute: a 27B/120B grinding a hopeless card through best_of_n + cross_model_carry is the worst-case burn, so early-park keyed on cross-family identical-failure signatures is highest-value on large models. The lms-ps/cascade subprocess waste (findings 3,4) is model-independent host-CPU overhead but scales with fan-out width — worst on wide DAGs run by a strong decomposer that produces many small-model leaves.

#### REVIEW steps — are they properly modelled?

**Current state:** Two weakly-coupled verification mechanisms plus a delivery gate, all triggered off the same awaiting_review transition. (1) Acceptance gate (nklein-acceptance-gate.ts) extracts one "Acceptance check: cmd" line from the card prompt, runs it in the Docker sandbox, classifies failures. Wired via runNKleinAcceptanceAutoRepair inside verifyNKleinTaskBeforeReady (runtime-state-hub.ts:418-439): on fail bounces a repair prompt (max 2 attempts) to the worker; on pass/missing/human_review just broadcasts task_ready_for_review. Runs fire-and-forget. (2) Second-opinion review (review-loop.ts to review-orchestration.ts to nklein-second-opinion-review.ts to live second-opinion-review-runner.ts): a reviewer-role session gets a seed prompt with the diff, worker reasoning, focus chain, board context, and calls submit_review approve/request_changes. decideReviewLoopAction has round-cap + stall + identical-loop park guards. Isolated review sandbox session (nklein-task-session-service.ts:2394+), nudged if no verdict, fail-safe to null. (3) Delivery gate (delivery-decision.ts + runtime-server.ts:560-595): pure gate over reviewApproved/testsPassed/regressionDelta/hasProtectedPathChanges x delivery tier to manual/commit/open_pr/merge. Order in finalizeHeadlessAutoReviewTask (runtime-server.ts:471-622): move to review, resolve sandbox result (result_branch/empty_patch/unknown), run review, if bounced/parked stop, else delivery gate, merge, complete + release deps. Trigger gating is isReviewableNKleinSummary accepting reviewReason hook/exit/attention/error. Decomposition has a separate quality assessment + re-decompose trigger but these are NOT modelled as review steps in the card lifecycle.

**Small-vs-large adaptation:** The current model treats a lone reviewer verdict as ground truth, which is backwards for the 4B-reasoning end where todo.md documents that weak reviewers over-approve, collapse to style nits, and never spontaneously run the acceptance command. Fixes should be capability-tiered via the catalog and selection: (1) For weak reviewers, correctness must be evidence-gated where acceptance present and passing is the real gate and the model opinion is advisory; never let a small model approve alone deliver, especially on an empty patch. (2) The reviewer decision role must be family-diverse from the architect so the second opinion is uncorrelated; this matters more the weaker the models, and a live run showed architect equals reviewer equals gpt-oss-120b, a decision-layer monoculture the selector should avoid. (3) Security and decomposition review should only be trusted to capable models; a small reviewer gets correctness-only and defers upward. (4) Escalation rungs, retrying on a stronger or different-family model before parking, are how a card a 4B cannot finish but a 27B or 120B can should climb, mirroring the acceptance auto-repair escalation the review loop lacks. Conversely for large-fast models the reviewer can be asked to run acceptance and do a real integration check cheaply, so dimensioned and integration review is affordable there. In short: the more capable the reviewer, the more judgment the gate may trust; the weaker it is, the more the gate must lean on executable evidence and diverse-model corroboration.
